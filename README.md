# Практическая работа №10. PHP MVC интернет-магазин: оформление заказа, валидация и формы

Дисциплина: Технологии разработки программного обеспечения.

## Используемый подход

Это продолжение MVC-магазина из практических работ №7 и №8 (Router, View, контроллеры, репозитории, namespace и autoload перенесены без изменений идеи). Работа №10 добавляет оформление заказа.

Задание предполагает, что корзина уже есть (шаг 9: «очистите корзину»). Отдельной работы с корзиной в этом репозитории нет, поэтому добавлена минимальная корзина в сессии: кнопка «В корзину» на странице товара, страница `/cart`. Больше в корзине ничего нет (нет удаления и изменения количества).

## Что сделано

- Маршруты `GET /checkout` (форма) и `POST /checkout` (обработка).
- Способы доставки в форме берутся из `data/delivery_methods.json`, в HTML они не прописаны.
- Валидатор `OrderValidator`: имя, email, способ доставки, адрес (только для курьера). У каждого поля своё сообщение.
- При ошибках форма показывается снова с введёнными значениями и сообщениями.
- После успешной проверки создаётся DTO `CheckoutData`, затем заказ `Order`, он сохраняется в JSON.
- После заказа корзина очищается и выполняется redirect на `/checkout/success`.
- Страница подтверждения показывает номер заказа, состав, способ доставки и итоговую сумму. Email и адрес на ней не выводятся.
- Страница `/check/orders` прогоняет сценарии из `data/order_cases.json` через тот же валидатор.

Технологии: PHP 8.0+, HTML, CSS. Библиотеки и composer не нужны.

## Требования

## Данные заказа

| Группа | Поля |
|--------|------|
| Контакт | имя, email |
| Доставка | id и название способа, цена доставки, адрес (только для курьера) |
| Состав заказа | список строк: id товара, название, цена, количество, сумма; сумма товаров; итог = товары + доставка |

DTO `CheckoutData` (имя, email, способ, адрес) содержит только данные формы. `Order` собирается в `OrderService` из DTO, строк корзины и выбранного способа доставки.

## Правила валидации (OrderValidator)

| Поле | Правило | Сообщение |
|------|---------|-----------|
| Имя | обязательное, 2-100 символов (после `trim`) | «Введите имя», «Имя должно быть от 2 до 100 символов» |
| Email | обязательный, `FILTER_VALIDATE_EMAIL`, до 100 символов | «Введите email», «Проверьте email» |
| Способ доставки | обязателен, должен быть в `delivery_methods.json` | «Выберите способ доставки», «Такого способа доставки нет» |
| Адрес | нужен только для курьера, 5-200 символов | «Укажите адрес доставки», «Адрес должен быть от 5 до 200 символов» |

Требование адреса задано по id способа доставки (`courier`), потому что в `delivery_methods.json` нет отдельного поля.

## Сценарии из order_cases.json

Страница `/check/orders`. Первые три сценария из dataset, остальные три добавлены, потому что задание требует отдельно проверить неизвестный способ доставки, а в dataset его нет (исходные три сценария не изменены).

| Сценарий | Источник | Ожидается |
|----------|----------|-----------|
| empty | dataset | ошибка (пустая форма) |
| bad_email | dataset | ошибка |
| ok | dataset | верно |
| unknown_delivery | добавлен | ошибка (`delivery = drone`) |
| courier_without_address | добавлен | ошибка (нет адреса при курьере) |
| courier_with_address | добавлен | верно |

## Сохранение заказов

- Заказы пишутся в `data/orders.json`. Пока файла нет, исходным списком служит `data/orders_seed.json` (пустой список).
- `JsonFile::write()` пишет сначала во временный файл `orders.json.tmp` с блокировкой `LOCK_EX`, затем заменяет им основной файл. Если запись не удалась, основной файл остаётся нетронутым.
- Если `orders.json` повреждён, чтение бросает исключение и новый заказ не пишется поверх повреждённого файла. Пользователь видит «Не удалось сохранить заказ», корзина не очищается.
- Номер заказа: максимальный существующий + 1.
- `orders.json` внесён в `.gitignore`, тестовые заказы в репозиторий не попадают. Сбросить заказы: удалить файл `data/orders.json`.

## Разделение ответственности

- **Controller** принимает запрос, вызывает валидатор и сервис, выбирает представление. Цепочки проверок в нём нет.
- **OrderValidator** проверяет данные, **OrderService** создаёт и сохраняет заказ, **CartService** работает с корзиной.
- **View** только выводит ошибки и данные, решений не принимает и файлы не читает.
- Redirect после POST: обновление страницы подтверждения не создаёт новый заказ.

## CSRF-токен (место для пояснения)

Механизм CSRF-токена в курсе не разбирался, поэтому в код он не добавлен. Куда он будет добавлен:

1. При показе формы (`CheckoutController::renderForm`) генерируется случайный токен и сохраняется в `$_SESSION`.
2. В форму `views/checkout/form.php` добавляется скрытое поле с токеном.
3. В `CheckoutController::submit` токен из `$_POST` сравнивается с сохранённым до валидации. При несовпадении запрос отклоняется.

- Шаг 10: страница подтверждения (номер, состав, доставка, итог, без email и адреса).

## Ограничения

- Корзина минимальная (нет удаления и изменения количества).
- Остаток товара не уменьшается после заказа.
- JSON-хранилище не рассчитано на одновременные заказы: два запроса одновременно могут получить один номер.
- Нет защиты от CSRF (см. выше), нет авторизации, платежей и писем.
