# Ответы на контрольные вопросы

1. **Какие входные данные получает приложение и где они находятся?**
   Файлы `data/delivery_methods.json` (способы доставки), `data/order_cases.json` (сценарии проверки), `data/orders_seed.json` (начальный список заказов), каталог (`products.json`, `categories.json`), маршруты (`routes.csv`) и POST-поля формы (`name`, `email`, `delivery`, `address`).

2. **Какой участок кода преобразует данные в интерфейс?**
   `CheckoutController` готовит данные (корзина, способы доставки, ошибки, введённые значения) и вызывает `View::render`, а `views/checkout/form.php` выводит форму, `views/checkout/success.php` подтверждение.

3. **Какое ошибочное состояние проверялось вручную?**
   Пустая форма, неверный email, неизвестный способ доставки, курьер без адреса, пустая корзина, отсутствие `delivery_methods.json`, повреждённый `orders.json`.

4. **Какие части решения вы бы изменили при увеличении объёма проекта?**
   Заменить JSON-хранилище заказов базой данных (изменится только `OrderRepository`), добавить CSRF-токен, управление корзиной, уменьшение остатка при заказе, транзакции, письма с подтверждением.

5. **Как проверить работу после чистого клонирования?**
   `git clone`, затем `php -S localhost:8000 -t public public/index.php`, затем пройти `docs/checklist.md` и открыть `/check/orders`.

6. **Какая ответственность у Controller, Model и View?**
   Model описывает данные и проверяет их (`Order`, `CheckoutData`, `DeliveryMethod`). Controller принимает запрос, вызывает валидатор и сервис, выбирает представление. View только выводит данные и ошибки.

7. **Почему Router не должен формировать HTML?**
   Router отвечает только за выбор обработчика по методу и адресу. Если он будет выводить HTML, логику маршрутов и внешний вид нельзя менять независимо.

## Дополнительно для защиты

**Почему после POST redirect?** Без него обновление страницы (F5) повторило бы POST и создало второй заказ. После redirect браузер делает обычный GET `/checkout/success`.

**Почему ошибки формы это нормальный сценарий?** Контроллер не бросает исключение при неверных данных. Он возвращает ту же форму с `errors` и `old`, статус ответа 200.

**Почему DTO создаётся после валидации?** `CheckoutData` и `Order` должны содержать только проверенные данные. Если создать объект раньше, в системе окажется заказ с некорректными значениями.

**Как защищена запись JSON?** `JsonFile::write` пишет во временный файл с `LOCK_EX` и затем переименовывает его. Если запись не удалась, основной файл не повреждается. Повреждённый `orders.json` не перезаписывается, потому что чтение бросает исключение до записи.

**Почему корзина в сессии хранит только id и количество?** Данные о товаре (название, цена) берутся из репозитория, поэтому цена не может быть подменена в сессии.

**Почему адрес обязателен только для курьера?** Правило описано в `DeliveryMethod::requiresAddress()` и применяется в `OrderValidator`. В `delivery_methods.json` отдельного поля нет, поэтому правило задано по id `courier`.

**Показать использование dataset:** изменить цену курьера в `delivery_methods.json`, обновить `/checkout`: цена в форме изменится без правок кода.
